## Configure the staging pair

1. In the authorized Vercel team, create or select separate staging web and API projects, rooted at `apps/web` and `apps/api` respectively. Use the same reviewed revision and supported Node LTS on both. Enable **Include source files outside of the Root Directory** so Vercel can use the root lockfile and shared contracts. Keep the default npm workspace install. The web config builds contracts before the Vite bundle and emits `dist`. On the Express project, ensure its build runs `npm --prefix ../.. run build:contracts && npm run build` before the function uses the contract package. Use the request-driven Express deployment, with no separate dev server process. [Vercel monorepos](https://vercel.com/docs/monorepos/monorepo-faq) · [Express on Vercel](https://vercel.com/docs/frameworks/backend/express)
2. Set the API's `FRONTEND_URL` to the exact staging web origin. Both API rules in `apps/web/vercel.json` target the staging API origin, preserving the request path. The web project uses `VITE_API_BASE_URL=/api/v1` and the browser stays on the web origin. The ordered API routes precede filesystem and SPA handling. Verify the upstream API origin is reachable through this rewrite under the project's deployment protection. A protection challenge in the rewrite is a blocker. [Vercel rewrites](https://vercel.com/docs/routing/rewrites) · [Vercel deployment protection](https://vercel.com/docs/deployment-protection)
3. Prepare an empty staging PostgreSQL database and a separate role for its API access. Apply the ordered migrations to the staging database through the provider's direct migration endpoint and `database/migrate.ps1 -Database <staging-db>`, with connection details supplied via the documented PostgreSQL configuration. Inspect the migration checksum ledger and rerun it before verification. Use a provider-supported, TLS-protected pooled endpoint for `DATABASE_URL`, with a serverless connection budget and a runtime role limited to the staging database. The app creates a module-level pool capped at five connections per instance. Verify aggregate usage against the provider's pool metrics because multiple instances may run. [PostgreSQL migration setup](PHASE05_POSTGRES.md)
4. Keep secrets in the API project only. Set fresh `JWT_ACCESS_SECRET`, `CSRF_SECRET`, `CRON_SECRET`, a dedicated staging `REDIS_URL`, and `APP_MODE=local`. Use `FOOD_ADAPTER=fixtures`, `AI_ADAPTER=disabled` and `SCHEDULER_MODE=manual-dry-run` for initial smoke tests. The secure production runtime requires HTTPS and `EMAIL_ADAPTER=emailjs` with a staging sender and two distinct active verification/reset templates. Configure `EMAILJS_SERVICE_ID`, `EMAILJS_PUBLIC_KEY`, `EMAILJS_PRIVATE_KEY`, `EMAILJS_VERIFY_TEMPLATE_ID` and `EMAILJS_RESET_TEMPLATE_ID` through the API project's environment settings. Use account mail only with an explicitly authorized test inbox. Without these staging resources the secure deployment check is blocked. [EmailJS setup](PHASE21_EMAILJS.md)
5. For private-file checks configure a separate private Supabase bucket and staging S3 credentials in the API project. Use `STORAGE_PROVIDER=supabase` and the existing `STORAGE_ENDPOINT`, `STORAGE_REGION`, `STORAGE_BUCKET`, `STORAGE_ACCESS_KEY` and `STORAGE_SECRET_KEY` settings. Keep staging storage private and isolate its objects and cleanup from other environments. [Private storage setup](PHASE07_LIMITS_UPLOADS.md)

## Groq and food recognition

To enable approved sample recognition, set `AI_ADAPTER=groq-synthetic`, `GROQ_API_KEY`, and `GROQ_MODEL=qwen/qwen3.8-27b` in the API project and redeploy. Keep `APP_MODE=local`, EmailJS and Redis configured. Signed-in users can analyze approved sample images through Food recognition.

For local sample testing, use the synthetic-demo configuration from Phase 19 with the test mailbox. Real user-photo analysis requires a separate authenticated upload path and approval of the provider, data handling and audience. With Groq configured, health reports `"ai": true`. Verify a signed-in sample request separately to confirm Groq access. Barcode lookup and manual meal entry continue to work when AI is disabled.

## Collect verification evidence

| Gate | Check on the actual staging pair |
| --- | --- |
| Rewrite and SPA | From the web origin, open and reload `/app/meals` and load its JavaScript and CSS. Confirm `/api/v1/health` returns API JSON, a signed-out request to `/api/v1/auth/me` returns 401, and an unknown `/api/v1/auth/does-not-exist` returns a JSON 404. Check that static assets return their expected media type. |
| Cookie lifecycle | Use an authorized staging account. On the web origin inspect sign-in and refresh response attributes for host-only `__Host-` cookies with `Secure`, `HttpOnly`, `SameSite=Lax` and `Path=/`. Verify reload, two-tab refresh, and sign-out. Confirm logout clears the matching cookies and an authenticated call after logout returns 401. Retain only attributes and statuses in evidence. |
| Database pooling | Exercise concurrent authenticated reads from staging accounts and inspect connection usage on the staging pool. Verify queries and requests remain within the assigned budget, no connection error appears, and results stay scoped to the caller. Document measured counts and configuration. |
| Private files | Verify upload, finalize, owner read, expired signature rejection, anonymous and cross-owner denial, and deletion with a synthetic image. Confirm no public object read is possible and keep object URLs and signatures out of evidence. |
| Exposed capability | Compare `/api/v1/health` and signed-in notification settings. Confirm unsupported reminder times and arbitrary image uploads fail before contacting a provider. If Groq is disabled, verify fixture analysis is also unavailable. Keep `NOTIFICATION_TEST_RECIPIENT` unset for the standard dry-run configuration. |
| Manual Cron auth | Call `GET /api/cron/process-notifications` on the API origin with no token and a deliberately wrong token and expect 401. With the correct bearer supplied through a secure client, expect a bounded dry-run result. Confirm no jobs were claimed or sent. Record statuses and run ID. |
| Scheduled Cron auth | Observe a real Vercel execution for the isolated staging API project's **Production deployment**, which is the Vercel environment that triggers legacy Cron. Identify the scheduled UTC window, deployed revision and run ID in the staging project logs. A manual request, including dashboard **Run**, only establishes endpoint behavior. |
| Email limits and delivery | Record the staging provider's active plan, template capacity, remaining quota, and sender limits. Verify Redis pacing/limits separately from EmailJS acceptance. For an explicitly authorized inbox, record acceptance of an account email and observed inbox receipt separately. Scheduled email requires its own authorized test recipient and two additional distinct templates under app validation, which can exceed the available plan. Leave it inactive and record that blocker if those resources are unavailable. |

Confirm the project has legacy Cron enabled and observe the execution in Vercel logs. No bearer, session cookie, database URL, verification link or signed object URL belongs in the verification record.
