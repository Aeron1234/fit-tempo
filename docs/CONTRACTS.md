Frozen for Phase 04 on November 16, 2026 (Asia/Manila). ARCHITECTURE.md remains authoritative. Executable transport schemas live in packages/contracts/src and are exported through @fit-tempo/contracts. Keep the Phase 03 health exports compatible. Review and version any later change to wire meaning, bounds or snapshots with affected consumers.

## Shared representation

Use UUID identities for persisted entities and client operation IDs. Scope client operation IDs by authenticated user and operation type. Use safe nonnegative integer revisions, starting at zero. Reject unsafe integers, fractional revisions and coercion from strings. Reject a mutation before exhausting the representable revision range.

Use canonical nonnegative decimal strings for measured quantities, money and nutrients. This freezes the wire representation more precisely than the architecture's illustrative JSON numeric examples. Allow at most nine integer digits and six fractional digits. Accept zero as "0" and omit redundant leading/trailing zeroes. Reject exponents, negative amounts, empty strings, NaN and Infinity. Positive quantities exclude zero. Transport these strings into PostgreSQL numeric without an intermediate floating-point calculation. Use explicit units. Fixed unit factors may convert grams/kilograms and milliliters/liters. Cups/spoons/counts require validated food-specific evidence before conversion to mass. Preserve raw/cooked and per-serving/per-100g basis. Do not assume all nutrient energy totals equal a macro formula.

Currency is an uppercase three-letter identifier. Syntactic validation does not establish a supported price currency. Services must check supported currencies and reject cross-currency arithmetic. Cost estimates retain unknown necessary prices and unknown within-budget status. Zero is an explicit known value. Never convert null nutrients or prices to zero.

Roles are trainee/admin. Role values on transport objects never authorize privilege changes. Server role/status/session checks remain authoritative. Source identity is a structured tuple with source kind, original external identity and revision context. USDA and Open Food Facts IDs are bounded numeric strings, distinct from internal UUIDs. Preserve leading zeroes and never cast them to integers. Local curated/user source IDs are UUIDs. Preserve provenance and source attribution independently of a user-editable display name.

## Recorded time and daily status

Use UTC ISO instants with Z. Store an IANA timezone name and the derived real Gregorian local date alongside the event instant. Validate calendar dates, supported timezone names and instant/date agreement. Millisecond precision and years 0001–9999 are the v1 interchange boundary. Do not trust an arbitrary supplied local date. A later preference change affects future entry defaults and does not regroup historical records. Deliberately editing an occurrence time recomputes date context using the entry's chosen zone and reopens affected tracking days atomically.

Group historical daily coverage using stored local dates. Do not recompute them with the current profile timezone. Preserve the recorded zone in exports and explain mixed-zone periods. Local-date keys are calendar labels, not a promise that every day lasts 24 hours. Recurring wall-clock availability and fixed UTC appointments have distinct semantics. Future scheduling implements the architecture's DST policy: move nonexistent times to the next valid instant and use the first repeated occurrence once. Phase 04 does not implement recurrence expansion.

Daily state is unrecorded, partial or complete. Unrecorded has no entries and no completion confirmation. Partial has entries without confirmation. Complete requires explicit confirmation, including an intentional zero-entry day. Changes reopen completion. Store one status identity per user/category/local date. Nutrient coverage is separate: a complete day may still have unknown protein for a logged item. Aggregate results retain known subtotals, logged-day coverage and missing nutrient counts. Do not call an incomplete subtotal a complete total.

## Error and response semantics

Return data envelopes for success and error envelopes with a stable code, safe message and requestId for failures. Use 400 for invalid input, 401 for missing/inactive authentication, 403 for CSRF or forbidden actions, 404 for absent/hidden owned resources, 409 for revision/idempotency conflicts, 413 for excessive payloads, 429 for enforced quota and 503 for dependency failure. Distinguish quota enforcement from unavailable limiter storage. Never reflect credentials, body measurements, raw prompts or arbitrary provider errors.

Conflict responses carry the current authoritative revision only after authorization. Revision-checked schedule/pantry requests carry expected revisions and a client operation ID, never trusted actor IDs, role assignments, computed nutrient totals, receipt digests or receipt results. Day-status requests carry only complete/reopen state, with category/date in the route and ownership derived from the session. A successful new mutation advances the relevant revision exactly once. Retried successful mutations return the original committed result even when the current revision has since advanced. Responses must enable consumers to invalidate/refetch authoritative data after conflicts.

## Transaction protocol

The following ordering is mandatory for schedule acceptance, pantry deductions and other revision-checked retryable writes. Request parsing and the pure decision helper do not replace this database protocol.

1. Validate the request against its strict schema. Authenticate the active session, enforce CSRF and derive the actor from the session. Verify the addressed owned resource without leaking other owners' records.
2. Canonicalize the parsed request for its operation. Include the operation type, route resource identity and all mutation-relevant fields, including the expected revision. Recursively sort object keys by UTF-16 code unit order, retain array order, serialize JSON without whitespace and hash its UTF-8 bytes using SHA-256. Decimal strings retain their canonical spelling. UTC instant spelling is retained exactly after validation. Equivalent second/fraction spellings count as changed input under digest v1, so clients must retry the original serialized request. Omitted fields and explicit null remain distinct. Do not insert time-dependent defaults into this digest. Freeze this digest algorithm as v1.
3. Begin the database transaction and lock the user's applicable revision row. Lock order is schedule then pantry if a later operation genuinely requires both. Every writer affecting the scope uses that same lock. Lookup the receipt by authenticated user, operation type and client operation ID inside the transaction. Resource identity is part of its digest, so key reuse for another resource conflicts.
4. If a receipt exists and its digest matches, return its original immutable result reference/commit summary before checking stale revisions or proposal expiry. Reauthorize access before returning any result. If the digest differs, return IDEMPOTENCY_CONFLICT (409). Never replay another user's receipt. The internal decideMutationPrecondition helper freezes this decision ordering for already-scoped, validated inputs.
5. Without a receipt, compare expected/current revision. A mismatch returns REVISION_CONFLICT or the domain-specific schedule conflict (409), with no mutation or receipt. Revalidate proposal expiry, feasibility and every related resource against current database state. Reject invalid/retired/version-changed dependencies as appropriate before applying writes.
6. Apply all related changes, increment the scope revision once and insert the unique receipt in the same transaction. Store the original immutable commit result/summary so future replay does not return a newly edited live resource as if it were the original result. Avoid sensitive duplication. A receipt's UUID resultReference identifies that durable commit result. Do not include signed URLs or other expiring secrets in a receipt.
7. Commit before returning. Rollback leaves neither effects nor receipt. A lost HTTP response is recovered by retrying the identical operation. Serialize concurrent requests through the revision lock and reinforce receipt uniqueness in PostgreSQL. Constraint races require a rollback/retry of the transaction and re-reading the winning receipt. Never silently treat a changed-payload conflict as success.

Retain deduction, completion and acceptance receipts for their owning record's lifetime. Account erasure removes receipts along with owned data. Missing authorization, malformed inputs and failed attempts do not create successful receipts. No network email send occurs inside a database transaction.

## Operation-specific invariants

| Operation | Atomic boundary and invariants |
| --- | --- |
| Accept schedule proposal | One revision per user. Availability, equipment/rest constraints, timezone and occurrence edits increment it. Verify proposal owner/base revision/expiry and current routine versions. Preserve completed sessions. Apply the confirmed changes, increment revision, cancel obsolete pending reminder jobs, insert revision-keyed replacement jobs and receipt together. No feasible slot produces an explicit no-fit result rather than stacked sessions. |
| Deduct pantry plan | Confirmation saves an estimate without reserving stock. Allocate each lot at most once across all recipes within the preview. On separate confirmed deduction, lock user pantry revision and recheck lots, units and shortage quantities. Use known expiry dates first, then undated lots, ties by ID. Expired/unusable inventory must not be recommended as safe. Deduction cannot make quantities negative. Store lot allocations and receipt with the single revision increment. Logging a meal is a separate confirmed action. |
| Confirm/reopen day | Key by session user/category/local date. Explicit completion may record zero entries. Log insertion/edit/deletion reopens affected categories/dates in the same transaction. Do not infer complete tracking or achievement from missing records. Nutrient/source coverage stays independent of day state. |

## Related resources and immutable history

Check visibility on every referenced food, recipe, exercise, routine, workout and file inside its write transaction. Permit owned resources and approved shared catalog resources only where that relationship permits them. A shared label or null owner is not enough without approval. Private links require the same owner, and files require ready state. Admin role does not confer default private-history access. These schemas describe representation. Services and constraints enforce visibility.

Capture immutable versioned snapshots when the user confirms a log or completes a workout. Retain ingredient quantities, conversion evidence, source identities, nutrition basis, nutrient unknowns, cooked yield and serving count for recipes/meals. Retain exercise names, measurement type, units, routine targets, variant identity and actual sets for completed workouts. Catalog edits/retirement must not rewrite snapshots. Corrections create an explicit revised history record/snapshot and preserve the audit/version relationship. TypeScript readonly/schema freezing helps avoid accidental object mutation but is not database immutability or authorization.
