# Fit Tempo error UI and account screen refresh

Copy the instruction block below into a new Codex chat opened in the Fit Tempo project.

```text
Implement a focused error UX update and redesign Fit Tempo’s sign-in and create-account screens. Help users understand what happened, what happened to their work, and what they can do next. Use short plain-language copy and one clear primary recovery action where practical. Preserve the existing theme, solid background, navigation behavior, routes, and confirmation flows.

Read AGENTS.md, ARCHITECTURE.md, docs/IMPLEMENTATION_STATUS.md, docs/DESIGN_SYSTEM.md, docs/CONTRACTS.md, docs/FRONTEND_ERRORS.md, and docs/BACKEND_ERRORS.md. Apply the Fit Tempo development skill and use the project-local Modern Web Guidance search and retrieve workflow before editing HTML, CSS, or client-side JS. Look up patterns for accessible form errors, announcement of status messages, and focus after navigation.

1. Build on the existing route fallback and shared GlassPanel. Give missing pages and unexpected route failures distinct copy and recovery. Keep the authenticated shell and saved theme where the shell can still render. Give public fallbacks a safe sign-in action and signed-in fallbacks a Today action. Use an explicit Reload action for route crashes when appropriate.

2. Normalize errors at the shared API/session boundary. Preserve validated status, known code, request ID, optional current revision, and valid retry metadata where available. Distinguish offline or network failures, timeouts, intentional cancellation, invalid responses, and API errors. Keep existing session refresh, CSRF, account isolation, and generic account recovery behavior. Map failures to safe, feature-specific UI copy without displaying raw exceptions, server HTML, or provider messages.

3. Present errors where users can act. Put validation beside the field with linked help. Retry failed reads in the affected card. Keep authorized cached data visible during failed background refreshes. For stale revisions and schedule or pantry conflicts, retain the current account's draft where safe and guide the user to reload and review. If a write timed out, explain that the outcome could not be confirmed. Check current state or use the existing receipt contract with the same key and payload. Avoid automatic replay of uncertain writes.

4. Prioritize sign-in, Today, Meals, Planner, Fit My Week, and Workouts, then audit remaining screens for inconsistent or raw error copy. Keep messages readable at 320px, with visible focus, useful action labels, and no dependence on color. Announce new inline errors once. On a full-page error, focus the heading. Verify recovery controls with keyboard and touch.

5. Normalize backend failures only where the current contract requires it. Generate request IDs before JSON parsing, map malformed JSON and oversized payloads to the existing 400 and 413 codes, and preserve existing status, authorization, and conflict behavior. Keep response envelopes compatible, and use sanitized diagnostics tied to the request ID for unexpected failures.

6. Redesign /sign-in and /register using the attached image as a composition reference. On wider screens, use a shared two-column layout with a feature carousel on the left and a solid account form on the right. Give each form a clear heading, a visible link to switch between Sign in and Create account, and one prominent submit action. Use Fit Tempo branding, original product visuals, and its existing light and dark tokens. Keep decorative visuals contained within the carousel panel and retain the solid full-page canvas. Only show authentication options and legal links that have working destinations in Fit Tempo.

7. Make the carousel about existing Fit Tempo features. Use three slides for Pantry and Budget Meal Planner, Fit My Week, and meal and workout tracking. Give each slide a short title, one sentence explaining the benefit, and an original visual or accurate product preview. Share the carousel across both routes. Make it user-controlled with labeled Previous and Next buttons and an accessible current-slide indicator. Keep slide height stable, support keyboard navigation and visible focus, and respect reduced motion.

8. At phone widths, render a single column with the form first and a compact carousel below it. Users should reach the fields and submit without scrolling past promotional content. Use full-width inputs where helpful, stack fields before they become cramped, and keep controls reachable when the keyboard opens. Reuse the existing fields, validation, verification, password recovery, session logic, and submission handlers. Show errors beside the affected fields or form action, preserve safe draft values after a failed submission, and keep links available for recovery.

Verify unknown routes, a render error, offline and timeout handling, intentional cancellation, expired sessions, field validation, revision conflicts, rate limits, provider outages, malformed responses, and a failed or unconfirmed save. Include a regression check that retry cannot duplicate a confirmed transaction. Run typecheck, lint, build, and relevant contract, frontend, and API tests. If browser access is authorized, check both themes at 320px, 360px, tablet, and desktop widths. On both account routes, verify carousel controls, form access with the phone keyboard open, switching between forms, validation, verification guidance, and recovery links. Record actual results and any browser blocker in the implementation status. Update the error guides and supporting project guidance when behavior changes.
```
